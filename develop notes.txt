- Synology DSM package
- Being security-hardened with setuid helper binaries, conf/privilege declarations, and self-healing ownership logic
- Grew into a full manifest-driven package with Info/Tools tabs, clickable hyperlinks in module output, self-healing ownership, and a DSM Application Privileges registration fix
- Part of the security overhaul that replaced sudoers-based privilege escalation with setuid helper binaries
- A UPS-client-check script running inside Syno_Toolbox needed the full path to `nmblookup` (`/usr/local/bin/nmblookup`) — bare `nmblookup` gave "not found" when run from within the package
- Wants to add a network-speed module to Syno_Toolbox showing download (and maybe upload) speed at a glance; was considering adapting Syno_iperf3_Speedtest's speedtest.sh and embedding Ookla Speedtest binaries, but Ookla's CLI takes ~1 minute per run
- Found that after a DSM update, first boot opening Syno_Toolbox hung the desktop (cursor/progress bar, Package Center icon unresponsive) — traced to `start-stop-status`'s `start)` case running `synotoolbox-helper runboot` (which backs up synoboot/synoboot1/synoboot2) synchronously instead of backgrounded
- Adding a Wake-on-LAN feature to Syno_Toolbox with a device dropdown populated via a bundled `arp-scan` binary (copied from SynoCli Network Tools) for local network device discovery
- Found that on multi-LAN DSM models using Open vSwitch, the physical `ethN` interfaces are enslaved to `ovs-system` with no IP, and the real IP lives on a virtual `ovs_ethN` interface instead — confirmed on his NAS named Oscar (LAN5/`ovs_eth4` = 192.168.20.200) and Senna (`ovs_eth0`); his DS925plus has no OVS and keeps the IP directly on `eth0`
- Hostname resolution for the WoL device dropdown uses `nmblookup -A <ip>` per discovered device; on Oscar this was ~103s sequential (each non-responding host hits nmblookup's ~10s NetBIOS timeout), backgrounding the calls got it to 12s (bound by one timeout), and wrapping each call in `timeout 2` got it to ~4s for 20 devices; `getent` is not available on his DSM to try reverse DNS as an alternative

## enable_ssh_root module (finished, working design)

`enable_ssh_root.sh` (bundled in Syno_Toolbox) sets root's SSH password and flips `PermitRootLogin yes` in `/etc/ssh/sshd_config`, with a companion `--disable` mode that reverts it. Final confirmed design, end-to-end tested on Senna (DSM7/DS720+) and Webber (DSM6/DS1812+):

- Flags via `getopt -o "" -l pwd,check,disable -- "$@"` — the `-o ""` is required; without it, `getopt` either errors outright ("missing optstring argument") when called with zero args, or silently drops recognized long options when args are present. `--pwd` triggers `read -rs pwd` (password arrives over stdin, never argv/`ps`); `--check` reports status read-only and exits before any mutation; `--disable` deletes the `PermitRootLogin yes` line (added via `sed ... a`, so removing it is a plain `sed ... d`, not a substitution) and exits.
- DSM6: enable/status of the SSH service is controlled by `synoservice`'s `ssh-shell` unit (not `sshd`/`synoservicectl`) — `synoservice --enable ssh-shell` / `--status ssh-shell`.
- DSM7: `synosystemctl enable/start sshd.service` is insufficient — it starts sshd on the default port 22 and never flips Control Panel's checkbox. The real mechanism (found via `strings` on `SYNO.Core.Terminal.so`) is the `SYNO.Core.Terminal` webapi; the fix is `synowebapi --exec api="SYNO.Core.Terminal" method="set" version="2" enable_ssh=true` (partial update confirmed sufficient — it pulls the configured `ssh_port` itself, no need to pass it), checked against `method="get"`'s `enable_ssh` field beforehand.
- Password is set unconditionally on every "enable" run (not gated on whether SSH/PermitRootLogin were already set), so the module doubles as a password-rotation action. The `sshd_config` restart is gated on a `restart_needed=yes` flag set only when the file was actually edited — enabling SSH or setting the password don't need a separate restart (DSM's own enable path already does a full daemon start).
- Backend password transport: `main.js`'s Enable button POSTs `admin_password` directly to the `run` action (bypassing `save()`/`toolbox.conf` entirely — a password must never be persisted to conf or passed as a CLI arg/argv, unlike e.g. `send_wol`'s `{mac}` placeholder pattern). `api.cgi` pipes it via stdin through the setuid helper unchanged (`execl()` preserves fds, so no code in the helper itself needs to touch it). `synotoolbox_api.sh`'s `run` case checks the module's manifest `secret_input: true` flag and, when set, calls the script directly with `--pwd` instead of routing through `run_module_script`'s normal `{field}`-from-conf substitution.
- `disable_ssh_root` is a second manifest entry (`hidden_row: true`, same script, `run_args: ["--disable"]`, no `secret_input` since it needs no secret) that shares `enable_ssh_root`'s UI row via a `companion_id` field on the enable entry; `main.js`'s `renderList` filters out anything with `hidden_row` so it never gets a row of its own, while `getstate` still reports it fine (full manifest object is spread through unmodified) so the Disable button's plain `run` call against that id works via the ordinary unmodified path.
- `check_args` auto-invokes a module via `checkModule()` on every page load — dangerous for a mutating module with no true dry-run branch (an earlier version briefly set root's password to the literal string `"check"` this way). Only safe once the script has a real early-exit read-only branch for it (or `check_args: null` to opt out entirely, as `send_wol` does).
